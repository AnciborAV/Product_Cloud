# Product Cloud: обзор кода

Проверка выполнена для основного приложения и самостоятельного `examples/bookshop`.
Это учебный проект с регистрацией, личным списком продуктов, корзиной и историей;
он не является подключённой к оплате и доставке торговой системой.

## Java 25 и структура

Основное приложение уже использовало Java 25, Spring Boot 4.1.1 и Maven.
Официальная [матрица Spring Boot](https://docs.spring.io/spring-boot/system-requirements.html)
подтверждает поддержку Java 25. Версии Spring-зависимостей согласует родительский POM;
произвольная замена библиотек ради номера версии не проводилась. Maven Enforcer
теперь выдаёт понятную ошибку при запуске сборки на слишком старой Java.

Сохранены constructor injection, разделение MVC / сервис / репозиторий,
BigDecimal для денег, record для DTO, Bean Validation, транзакции, CSRF и
получение владельца из авторизованной сессии. JPA-сущности намеренно не превращены
в record: ORM необходимы отдельные правила создания и отслеживания изменений.
Preview-возможности, виртуальные потоки и новые фреймворки без задачи не добавлялись.

## Что исправлено

| Наблюдение | Решение |
| --- | --- |
| В static лежало неиспользуемое дерево размером около 1 МБ | Удалён `images/1.png`; ссылок на него в шаблонах и CSS не было. Продуктовый баннер сохранён |
| Для числа в шапке загружалась и пересчитывалась вся корзина | Добавлен агрегатный запрос SUM с ограничением по владельцу |
| `record` защищал ссылку на список, но не сам переданный список | CartView и OrderView создают `List.copyOf` в компактном конструкторе |
| Массив аватара можно было менять через переданную/полученную ссылку | Добавлены защитные копии и проверка hasAvatar без копирования |
| Прямой вызов сервисов позволял обойти ограничения форм | AccountService и OrderService используют @Validated и @Valid |
| Публичный метод блокировки допускал вызов без транзакции | Установлен MANDATORY; изменения продолжают держать блокировку на всю операцию |
| История могла делать отдельный запрос для строк каждого заказа | Добавлена пакетная загрузка @BatchSize; пагинация заказов сохранена |
| Комментарии отсутствовали во многих новых классах | Русские пояснения к объявлениям Java, аннотациям, компонентам record и локальным объектам; единое форматирование |
| Код был сжат в длинные строки, встречались однобуквенные имена сущностей | Развёрнуто форматирование, понятные account/product/graphics, обычные импорты вместо длинных полных имён |
| В книжном примере отсутствующий id перемещения вызывал NullPointerException | Пустой идентификатор теперь проходит обычную ветку HTTP 400 |
| В книжном примере дублировались заголовки HTTP-ответа | ShopController использует общий Http.send |
| Временный URL предпросмотра фото удерживался до ухода со страницы | Явное освобождение URL и восстановление при возврате из кеша навигации |

Схема основных таблиц и существующие данные не удалялись. Изменения не требуют
пересоздания аккаунтов, корзин или истории. Семантика личного списка сохранена:
удаление из корзины оставляет продукт в списке, удаление из списка убирает его
из корзины, но не меняет прежний заказ.

## Проверки

- Основной проект: `./mvnw clean verify` на JDK 25; 34 теста без ошибок и пропусков.
- Проверены регистрация, настоящий вход, CSRF, изоляция владельцев, ошибки форм,
  корзина, очистка списка, сохранность исторических цен, повтор токена оформления.
- Добавлены проверки агрегата шапки, защитного копирования, валидации сервисов,
  требования транзакции для блокировки и отката всего повторяемого заказа при ошибке.
- Проверены отсутствие `/images/1.png` и доступность нужного продуктового баннера.
- Самостоятельный пример компилируется на JDK 25 с `release=17`;
  5 тестов без БД проходят, 5 PostgreSQL-сценариев локально пропускаются без отдельной БД.
- Существующие GitHub Actions дополнительно проверяют PostgreSQL 16 и браузерный
  сценарий регистрации с фото, кабинета, корзины, удаления и оформления заказа.
  Для книжного примера CI запускает PostgreSQL-тесты на JDK 17 и 25.
- Локальный Chromium скачать не удалось: сервер загрузки вернул некорректный архив.
  Поэтому локальная визуальная проверка браузером не заявляется; результат CI
  следует смотреть в Checks соответствующего pull request.

Для тестов используется отдельная база с create-drop. Пользовательскую базу
к тестовому профилю подключать нельзя. Настройки сетевого прокси проверочной среды
в репозиторий не включены.

## Что остаётся ограничением

1. Hibernate `ddl-auto=update` удобен для обучения; для публичной эксплуатации нужны
   версионируемые миграции, резервное копирование и проверка восстановления.
2. Подтверждение email, восстановление пароля, ограничение попыток входа основного
   приложения, оплата и доставка пока не реализованы. Смена пароля завершает
   текущую сессию, но не все сессии пользователя на других устройствах.
3. Требуются HTTPS и Secure-cookie при публичном размещении. Проверка доступа
   и CSRF уже включены, но это не полноценный внешний аудит безопасности.
4. Корзина и полная очистка списка работают с коллекциями в памяти. Для очень
   больших личных списков следует определить продуктовые лимиты и перейти к
   пакетным операциям с соответствующими нагрузочными тестами.
5. Одновременное редактирование профиля в нескольких сессиях не имеет отдельного
   интерфейса разрешения конфликтов. Действует обычная транзакционная модель БД.
6. Книжный пример — локальное приложение одного владельца; PDF проверяется по
   размеру и сигнатуре, без антивирусного сканирования. Его сессии живут в памяти.

Подробность комментариев выбрана для изучения. В рабочей команде обычно сокращают
очевидные пояснения и оставляют прежде всего причины решений и важные ограничения.
